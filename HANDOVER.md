## How to keep this file useful

After every round of code changes, before or with its commit:

1. Update **Last updated** above.
2. Update **Current status** and **Next steps** so they're true now.
3. Add any new decision to **Decisions** (date, what, why). Never rewrite old ones; if one is
   reversed, add a new entry that says so.
4. Add any change in scope to **Scope changes**.
5. Add a row to **Change log**. A commit can't contain its own hash, so write "this round's
   commit" and replace it with the real hash (`git log`) at the start of the next round.
6. Add or close items in **Open issues**.
7. If a version number changes, record it in **Versions**.
8. Update the `MAP` object at the top of the script in `docs/project-map.html` (milestones,
   parts, next step, the decision waiting on the user, today's changes) and the same data in the
   copy the user opens, `prototypes/Stationwagon Project Map.html` (the page wrapped in its own
   `<html>`; gitignored). It is no longer published as an artifact (the user, 2026-10-21)

Keep entries short and factual. Don't put passwords, keys or other secrets in this file.

## What Stationwagon is

Radio software for small stations that runs on ordinary **shared cPanel hosting**: AutoDJ with
real crossfades, a listener stream, and a browser (later Windows) studio for live shows. No root,
no Docker, no extra ports, no processes running all day. The first station is **Radio WordWave /
Radio WoordGolf**, a Christian station.

How it started: the station runs on AzuraCast at Asura Hosting (`a8.asurahosting.com`, station
`radio_wordwave`). Its Web DJ failed with "An error occurred with the Web DJ socket": the Web DJ
websocket proxy returns 502 on Asura's side. As a stopgap, the presenters broadcast with **BUTT**
straight to the Liquidsoap harbor on port 8345, which works. The user then asked for software
designed from scratch for shared hosting, and named it Stationwagon.

**Best-quality song prep** (round 51, the user's goals 1–8 of Next steps 17). **What happens to an upload now**: the browser decodes the MP3 at its own sample rate (no forced 44.1 kHz). If no mastering, no levelling and no rate change is needed, **the original goes up as it came** (nothing is encoded; `{keep}` from `prep-worker.js`). Otherwise the samples go, in this order, through the resampler (only when the rate changes: a Kaiser-windowed sinc, 23 kHz content left at −146 dB), mastering, levelling, silence trim and fades, at the station's **processing precision** (32-bit float, 24-bit or 16-bit, with or without TPDF **dither**), then once to 16-bit and **once into LAME 3.100** (`app/assets/vendor/lame-3.100.js`, built from source with Emscripten, `tools/build-lame-wasm.sh` and `tools/lame-wasm/swlame.c`), CBR with the bit reservoir on. **Sound & safety → Sound quality** has the new settings (`StationSettings`): Prepared songs (bitrate, default **160 kbps**, 224 and 320 added), Sample rate (**44.1 kHz for every song, the default**; 48 kHz; the song's own: see the Firefox limit below), Processing precision (default 32-bit float), Dither (default on) and Encoding quality, a slider 0–9 (default **9 = LAME -q 0**, the best). A song at a rate the station doesn't keep (e.g. 32 kHz) goes to the nearest family and **the uploader is told** before the work starts (`SwPrepCore.rateNote`, `onNotice` in `upload.js`). **LAME's own gain cut is undone**: LAME's presets turn the input down by 5 % at 160 kbps and below (0.95; 0.97 at 192, 0.98 at 224), which left every prepared song 0.26–0.45 dB under the station's target; `swlame.c` opens LAME, reads the scale and reopens with its inverse, so the stored −16 LUFS song now measures −16.00 (checked with LAME's own decoder, within ±0.003 dB). A bitrate LAME can't do at a rate is refused, not silently changed. **Measured against lossless music** (EBU SQAM, 12 items, and a 24-bit techno track, `quality_browser_test.mjs`): at 160 kbps the noise-to-mask ratio (a simple Brandenburg NMR over Bark bands up to 16 kHz) is −5.0 dB for LAME q0/q2/q5, −4.7 for q9, −4.1 with the reservoir off and −3.0 for lamejs (the old encoder); a whole upload against the lossless original improves from 16.6 → 22.8 dB SNR (ABBA), 12.6 → 17.1 (castanets) and 17.5 → 23.2 (techno), within 0.3 dB of one encode straight from the original; 24- and 16-bit precision give the same result as 32-bit; LAME q0 takes 3–4 s per minute of music. **Songs at 44.1 and 48 kHz in a row** play with no gap, drop, stall or wrong pitch on the station page, the stream-only page and the embed in Edge (`rate_switch_browser_test.mjs`, 25; turns heard 0.07–0.16 s from plan). **In Firefox** (159, `--firefox`, over WebDriver BiDi) the station page's two decks are exact too, but the stream-only page and the embed (hls.js) go quiet for 3.5–5.6 s where 44.1 kHz turns to 48 kHz and then play that much late (not again at the change back); forcing hls.js to repackage the MP3 into MP4 didn't change it. So **stations default to 44.1 kHz for every song** (the user's choice, 2026-11-09): one rate in the stream, a 48 kHz upload resampled once with no audible loss (22.9 vs 22.8 dB). **Songs made before this round are offered for re-levelling** (the user's choice): `Library::madeWithOldEncoder` (a levelled song whose file has no `STATIONWAGON_PREP` tag naming LAME 3.100; read once per file, kept in `storage/cache/prep-encoder.json`), `relevelList` marks them `old`, and the library's quiet line and Re-level panel say they were made with the old encoder, about 0.3 dB under the target; Re-level makes them again from their originals.
